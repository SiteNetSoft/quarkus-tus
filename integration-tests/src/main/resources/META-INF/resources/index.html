TUS console

Manual harness for the quarkus-tus extension. Every request is logged with the headers that carry the protocol, so you can watch it work. Not part of the published library.

Server capabilities

Every TUS client starts here. OPTIONS reports the protocol version, the size ceiling, the checksum algorithms, and which extensions this server implements.

Watch for: Tus-Extension — a client should only attempt what this lists.

Core upload

The heart of TUS: create an upload, send it in chunks, and resume from wherever it stopped. Pause mid-upload and press Resume — the client asks HEAD where the server got to and continues from that byte, which is what makes an interrupted upload survivable.

Watch for: each PATCH returning the new Upload-Offset, and the HEAD on resume reporting the same number the server last acknowledged.

Creation with upload

Sends the first bytes inside the creation request itself. For a small file that is the whole upload in a single round trip, which matters on high-latency links where the extra request costs more than the data.

Watch for: one POST only, answering 201 with an Upload-Offset already greater than zero.

Deferred length

For uploads whose size is not known when they start — a live recording, or a stream being transcoded on the fly. The upload is created with Upload-Defer-Length: 1 and the real size is supplied later, on a PATCH.

Watch for: HEAD reporting Upload-Defer-Length: 1 and no Upload-Length, until the PATCH that supplies it.

Checksum

The client hashes each chunk and sends the digest alongside it; the server rejects the chunk if its own hash disagrees. The SHA-1 here is computed in the browser. The corrupt case deliberately sends a digest of different bytes.

Watch for: the corrupt chunk answering 460, and the HEAD after it showing the offset unchanged — the bad bytes were never stored.

Parallel upload

Splits the chosen file into partial uploads, sends them at the same time, then asks the server to join them into one. On a fast link several connections finish sooner than one, and the merge happens server-side so the client never reassembles anything.

Watch for: the PATCHes interleaving in the log, then a final POST carrying Upload-Concat: final and a merged length equal to the whole file.

Expiry and termination

Unfinished uploads do not live forever: the server returns the moment an upload stops being resumable, and reclaims it afterwards. A client can also abandon one explicitly, which frees the storage immediately rather than waiting for expiry.

Watch for: Upload-Expires on creation, and after DELETE a HEAD answering 404 — the upload is genuinely gone.

Live events

Two server-sent streams report an upload as it happens, so a progress bar does not have to poll. Events carries the whole lifecycle — connected, progress, complete — and the server closes it when the upload finishes. Progress carries progress alone.

A stream needs an upload that has started but not finished, so the order matters: on Core upload pick a file and press Upload, then Pause; come back here and connect; then Resume. Events arrive below, ending in complete.
